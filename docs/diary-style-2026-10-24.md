# 日记体改造（2026-10-24）

> 用户原话：「视觉总结不是跟你说了吗要**像写日记一样**，还有 2026-08-13 的日报，**格式还是不对**」。
> 本文记录这两件事的真因、改法与验证证据。

---

## 一、日报格式不对：真因是代码，不是陈旧数据

`20-日报/2026-08-13.md` 实测 **1,477 行 / 138,652 字节**。结构：

```text
## 今天          ← 模型写的自然段（这部分一直是对的）
## 电脑使用      ← 应用/网站/专注段/时间线统计罗列
## 视觉总结      ← 61 片总结逐片原样粘贴
   **03:22-03:30**
   ## 关键操作
   - 06:03:30-06:04:16：…
```

先怀疑是 `publish` 搬运了旧快照。**验证后否掉**：库里 `output_text` 本身就是 76,342 字，
且 **751/753 篇**日报都带 `## 视觉总结` —— 是当前代码在产，不是历史残留。

而 `docs/spec/requirements.md` R12 写得很明确：

> 日报**只写突出部分**（前 6 应用 + 前 5 域名各一句 + 压缩时间线），
> **全量明细一律归时段网页** `10-时段/YYYY-MM-DD.html`。

片层总结属于全量明细，时段网页的「视觉」section 已逐片完整呈现（卡片、不折叠）。
日报再粘一遍只有坏处：文件膨胀、与网页重复、把叙事淹没。

**改法**：`render_narrative` 里那段逐片粘贴的循环换成一句指路。

| | 改前 | 改后 |
|---|---|---|
| 行数 | 1,477 | **216** |
| 字节 | 138,652 | **27,344** |
| 章节 | 今天 / 电脑使用 / 视觉总结 | 今天 / 电脑使用 / **展开看全量** |

## 二、视觉总结不是日记体

旧输出（796 字样本）：

```text
## 关键操作
- 06:03:30-06:04:16：在 Obsidian 章梗概笔记中梳理《基因飞升》第一卷的写作结构规则
- 06:04:51-06:05:30：继续编辑第四十一至四十六章的分线细分情节
```

**每条都带时间戳、都是「动作 + 对象」清单句** —— 这是审计日志，不是日记。

### 改了三层（因为只改提示词不够）

| 层 | 改动 |
|---|---|
| 1. 提示词 | `screenmemo-v1` 4.4 节：从「每条以区间开头、至少 3 条列表项」改成「连贯叙述、不带时间戳、不用列表」 |
| 2. 校验 R5 | 「每节 ≥3 条列表项」→「每节 ≥`MIN_SECTION_CHARS`(30) 字」 |
| 3. 新增 R5b | **检测列表项**，命中即判不合格，把理由回灌给 rework 循环重做 |

**第 3 层是实测逼出来的**：3 片测试里，`6c7912b97625` 与 `b330e5f1ec30` 输出了漂亮的叙述，
但 `42560c7b8038` **无视提示词**，仍输出 `- 这段时间的核心工作围绕…`。只靠提示词约束不住。

### rework 循环能纠正（实测）

同一片 `42560c7b8038` 加上 R5b 后重跑：

```text
耗时 456s  len=842  rework=5  列表项=0
```

正文变成：

> 先在分析 dsh 上下文系统的会话里逐条过了一遍架构决策表，确认了 M5 旧插件打补丁路线已停止、
> M4 cortex UI 和 M6 cortex Host 核心正在执行中…接着浏览了主会话准备记录和三条待办事项

代价是耗时上升（456s vs 347s，因为要多跑几轮 rework）。

## 三、过程中抓到的两个自身缺陷

### 缺陷 1：`--force` 参数没接线（静默零产出）

```python
futs = {ex.submit(run_one, it, args.blind): it for it in ids}
```

`run_one` 第二个参数是 `force`（透传 `enhance_slice`），却传了 `args.blind`。
新加的 `--force` **完全没生效**：3,735 片 **0.1 秒"跑完"**，`sum=0`，
全部命中已有结果直接返回，**模型一次都没调**。

这是最难发现的一类 bug：退出码 0、打印"成功 3735 / 失败 0"、日志一片绿，
唯一异常是耗时 0.1s 和 `sum=0`。**如果不看单条耗时，会以为大功告成。**

修：`args.blind or args.force`，哨兵 **T34f**。

### 缺陷 2：`--force` 的幂等判据会死循环

最初写成「全选含图片的片」。但批量是**多轮循环**（`--rounds 14`），
每轮 `pick_pending` 都会把上一轮刚做完的片重新选中 → 永远跑不完。

修：启动水位线 `_FORCE_BEFORE = int(time.time()*1000)`，只重做 `created_at < _FORCE_BEFORE` 的行。
哨兵 **T34e**。

## 五、教训

1. **提示词约束不住格式时，校验层必须兜底**。模型约 1/3 概率无视「不要列表」，
   只有把违规理由回灌重做才可靠。校验器不是"事后清理"，它是闭环的一部分。
2. **改校验规则要同时改合格样例**。T13 的样例还是旧的清单体，改完 R5b 后它自己就成了不合格，
   冒烟因此红了一次 —— 这是好事，说明哨兵有效。
3. **"跑完了"必须核对耗时与内容量**。3,735 片 0.1 秒、`sum=0`，
   如果只看"成功 3735 / 失败 0"就会误判完成。**判据要包含产出实质**，不能只看条数。
4. **加参数的同一轮就要验证它真的被用上**。`--force` 选片逻辑对了、参数也解析了，
   唯独最后一行 submit 没传 —— 参数存在 ≠ 参数生效。
