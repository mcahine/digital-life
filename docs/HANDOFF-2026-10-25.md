## §4 SDCA 第三步：原因追溯（为什么会长成这样）

不是为自己开脱，是因为**不了解成因就会用同样的方式再长一遍**。

| 现象 | 根因 | 证据 |
|---|---|---|
| `smoke.py` 长到 1,404 行 | **没有 pytest**。想验证一个想法，唯一去处就是往 smoke 里再加一条 `check()`。207 个调用点是一天一天加出来的 | `pyproject.toml` 无 pytest |
| `tmp/` 1,600+ 个文件 | **同上**。没有 `tests/`，验证脚本只能写在 `tmp/probe_*.py`，一次一个，从不回收 | `tmp/` 里 200+ 个 `probe_*/fix_*/patch_*` |
| `daily.py` 1,202 行 9 种职责 | 日报从「模板渲染」演化到「模型叙事」，每次都是**在原文件里加分支**，没有一次拆分；旧路径 `render_daily` 降级成别名保兼容，进一步黏住 | `render_daily` 是 `render_narrative` 的别名 |
| 呈现层 import 领域层私有符号 | `slice_pages` 是后加的呈现层，当时 `timeline_merge` 的内部函数是唯一现成的标题清洗实现，**直接拿了私有函数**而没有升格公开 API | 3 处 `_clean_title` |
| 发布层反向 import 加工层 | 用户 2026-10-24 裁决「日报不入库、每次现算」，`publish` 必须调 `build_daily`。**这个设计是对的**，问题是 `daily` 把取数和渲染焊死，别人只能整块调用 | `publish.py` 函数内 import `daily` |
| 数据现状「753 天只有 1 天有叙事」 | 只有 2026-08-13 那天跑过模型。**这不是 bug 是成本问题**：全量需 143 次调用（估算见 §6.3） | `daily_summary.narrative` 非空仅 1 天 |

## §5 SDCA 第四步：方案制定——下一手该怎么派发

### 5.1 派发模式（照搬本会话验证过的做法）

**Mode: parallel — 每个子代理独占写域，共享文件由主代理统一改。**

本会话实测有效的四条硬规矩，**第五条是新增的**：

1. **写域登记**：派发前点名每个子代理「只能改哪些文件」，并明确「不许改哪些」。共享文件（`smoke.py`、索引、计数文件）**一律留给主代理**。
2. **交付格式五段式**：P（计划+判据）/ D（改动文件+**真实代码片段**）/ C（命令+**真实输出**）/ A（系统性问题+建议条文原文）/ 未做与风险。**缺段视为未完成。**
3. **禁止自报即通过**：主代理在派发时**先建可对拍的基线**（本会话做了 `tmp/a0_baseline.json` 与叙事指纹），交付后逐项对拍。
4. **S41/S38**：子代理不得删任务范围外文件；不得 `git add -A`。
5. **🆕 资源预算**（本会话吃了亏）：**派发时同时声明资源约束**。三个子代理同时读 912 MB 库会互相拖慢；批量重生成期间禁止跑全库扫描。

### N1 视觉总结折叠（超过固定长度默认折叠）

**用户原话**：「视觉总结这块确实是需要有个折叠，超过固定长度就默认折叠，不然有些块就太长了」

**现状实测**：`slice_pages/vision.py` 里**没有任何 `<details>`**，`render_summary_md()` 把整段 summary 全量铺开。
2026-08-13 单页 494 KB、845 个 `<li>`；2026-08-07 是 3 设备日，更大。子片递归展开后单页可到 700 KB。

**要做的**：
1. 视觉卡片正文超过阈值（建议 **800 字**或 **12 行**，二选一，做成常量 `SUMMARY_COLLAPSE_CHARS`）时，
   默认折叠，显示前若干行 + 「展开全部（共 N 字）」。
2. **折叠用 `<details>` 原生元素**，不要 JS（项目设计禁令：不引框架；且 `base.py` 已有 `<details>` 用于网站段，风格统一）。
3. **父片与子片各自独立折叠**——子片本身可能就超长，不能因为「在父片里」就不折。
4. 折叠态要能被 `hourbar` 的锚点跳转自动展开（现有 `base.reveal()` 已处理 `<details>`，复用即可）。

**验收**：
- 单页体积显著下降（对比 2026-08-13 当前 494 KB，目标 **< 300 KB**）；
- `grep -c '<details'` 在视觉段 > 0；
- 任取一个超长 summary，其**全文仍在 HTML 里**（只是藏在 `<details>` 内，不是截断）——**这点必须断言**，
  否则就是「为了好看丢了内容」，与「片层总结不截断」的铁律冲突。

**预期收益**：视觉段是现在页面体积的主要来源（845 个 `<li>`）。这一条同时缓解 N4。

### N2 + N3 + N4 定位条重设计（合并做，分开做会返工两次）

**用户原话**：
> 「这个条里的时间线事件怎么做不到全部呢，还有要区分出不同设备的时间线。
> 这个条需要考虑到能够容纳几百、几千的事件，所以还需要再设计。
> 我能考虑的设计点就是：视觉总结和时间线分成两个段，这两个段按照设备又分出独立线，这样最大化避免的冲突」

#### 现状实测（这是 N2 的量化证据）

| 日期 | 设备 | 时间线全量 | 其中 ≥120s | 该设备覆盖率 |
|---|---|---|---|---|
| 2026-08-13 | pc-main | **653 行** | 65 | **10.0%** |
| 2026-08-07 | pc-main | **1771 行** | 59 | **3.3%** |
| 2026-08-07 | phone-1 | 19 行 | 9 | 47.4% |
| 2026-08-07 | phone-2 | 52 行 | 16 | 30.8% |
| 2026-10-01 | pc-main | 193 行 | 11 | 5.7% |

> **口径说明（我第一版写错过，这里留痕）**：`timeline.points(ctx)` 是**跨设备聚合**函数，
> 它内部遍历 `ctx.devices`。所以不能「给每台设备单独调一次 points 算覆盖率」——
> 那样每台设备都会拿到**全部设备**的点数，出现「19 行覆盖 84 点 = 442%」这种荒谬值。
> 正确做法：按设备数 `len(ctx.merged(dev))` 与逐行 `span_seconds >= 120` 过滤后计数。
> **这正是 S62 的同族错误：拿一个跨设备聚合结果去解释单设备口径。**

**根因**：`timeline.points()` 只收 `span_seconds >= MAJOR_SECONDS (120)` 的行（DL-18 明确定义的「有效点」）。
用户看到的「做不到全部」不是 bug，是**当初为了减少噪音而设的阈值**——但用户的真实需求变了：他要的是**全量定位**。

> ⚠️ **这条与 DL-18 冲突**：DL-18 写「有效点 = ≥120s」。N2 要求全部。**不是谁错，是需求演进了。**
> 处理方式见 §11.7。

#### 用户给的设计方向（我把它拆成可执行规格）

用户说的是「**两段 × 每段按设备分线**」：

```text
┌─ 定位条 ─────────────────────────────────────────┐
│ 时间线段                                          │
│   D-001      ├──●──●────●───●──────●───●──┤     │  ← 该设备全部时间线行
│   iQQQZ3     ├────●─────●──────●───────────┤     │
│   iQQQ Neo11 ├─●──────●────●───●───●───────┤     │
│ 视觉段                                            │
│   D-001      ├──■────■──■──────■──────■────┤     │  ← 该设备全部叶子片
│   iQQQ Neo11 ├────■───■───■──────────■─────┤     │
└──────────────────────────────────────────────────┘
```

这个设计对：**两个数据源的语义不同**（时间线是「持续行为」、视觉是「有截图证据的片」），混在一条轴上必然互相遮挡。
按设备再分线，解决了「pc 的 1771 行 vs phone 的 19 行」这种量级悬殊导致的挤压。

#### 规格

1. **两条独立的轴**：`时间线轴` 与 `视觉轴`，上下排列，各自有刻度（0–24h）。
2. **每条轴内按设备分行**（一设备一行）。只有当日**该段**有数据的设备才出这一行。
   例：某天 pc 有截图但 phone 没截图 → 视觉轴只有 pc 一行。
3. **点数上限与降采样**（N4 的核心）：
   - 单行超过 **~200 点**时必须降采样，否则 1771 个点挤在 1000px 里等于一条实心线。
   - 降采样规则：**按时间桶聚合**，每桶画一个「有事件」的标记 + 计数（如 `●3`），
     **不是丢掉事件**。用户点开桶仍然能看到该桶内全部条目（锚点跳到时间线对应位置）。
   - **桶宽自适应，但必须按「时间跨度」算，不是按「行数」算**（我第一版写错过，见下方说明）：
     ```python
     span_s = max(每个事件的 start 秒) - min(开始秒)   # 该设备当日的实际活跃跨度
     桶宽_s = clamp(ceil(span_s / 200), 60, 900)        # 目标 <=200 桶，最细 1 分钟、最粗 15 分钟
     桶数   = ceil(span_s / 桶宽_s)                     # 恒 <= 200（由上式保证）
     ```
   - **实测参考**（2026-10-25 真跑，见下表）：pc-main 2026-08-07 有 **1771 行、跨度 22.1 小时**
     → `ceil(79560/200)=399` 秒 ≈ 6.6 分钟 → **199 桶**。
   - ⚠️ **不要写成 `桶宽 = ceil(总行数/200)`**：行数是「条」，桶宽是「秒」，量纲不同。
     那个式子算出 1771→9，会被当成 9 秒，实际应为约 400 秒。**这是量纲错误，不是精度问题。**
4. **视觉轴的点 = 叶子片**（不是 slice 总行数，符合 DL-17）。
5. **锚点仍走单点生成**：`timeline.row_anchor()` / `vision.card_anchor()`，**不得自己造 id**（S65/DL-18）。
6. **图例必须注明降采样**：如「D-001 时间线 1771 条 → 按 9 分钟聚合为 197 点」，
   否则用户会以为这就是全部——**这是「数据完整性可观测」，比好看重要**。

#### 验收（必须逐条给真实输出）

- **零丢失对拍（原式不成立，已修正）**：不要写 `桶数 × 桶覆盖 = 总行数`——
  桶宽是时间、覆盖是秒数，两边量纲不同，等式不成立。正确的三条并列断言：
  ```text
  ①行数守恒：Σ(每桶内事件数) == 该设备时间线总行数     # 一条都不能丢（硬要求）
  ②桶数受限：桶数 <= 200                               # 可读性约束
  ③桶内可追：点开任一桶，其 href 能定位到该桶第一条事件的锚点
  ```
  **三者分开断言，不要合成一个等式。**
- 全页 `id=` 无重复（S65）；
- 每个点/桶的 href 都能在全页找到同名 id；
- 单页体积对比 N1 前后；
- **S20 注入验红**：把降采样改成「直接截断前 200 条」，零丢失断言必须变红。

#### 性能约束（别踩旧坑）

`1771 行 × 3 设备` 每天渲染，**循环里不得出现 SQL**（DL-9）——一次批量取回后在内存里聚合。
参考：`load_slices` 曾因循环查库从 1.6s 退化到 103s，753 页从 40 分钟变 5 小时。
