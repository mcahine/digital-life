## ⚠️ max_tokens 上限 bug（2026-10-23 修）

批次里出现过 2 次致命失败：

```
LLMError: 上游返回 400：field MaxTokens invalid, should be in [1, 65536]
```

**根因链**：空内容自救重试 → `bigger = max(max_tokens*4, 4096)` **没有封顶** →
调用方已按 65536 发送时被放大到 **262,144** → 上游 400 → 因为是 400 而不是
`EmptyContentError`，外层「空内容重试」循环收不到 → 整片 FAIL，白烧 8 分钟。

**连带发现**：即使加了封顶，`if bigger <= max_tokens: raise` 会把「已到上限」
误判成「无法放大」而直接放弃。该模型 reasoning 暴涨是随机的，**同一预算重发常常就出内容**。

修法两处：
1. `MAX_TOKENS_CAP = 65536`，放大路径一律 `min(cap, ...)`
2. 已到上限时**不放大但仍原样重发一次**（`if bigger < max_tokens: bigger = max_tokens`）

回归断言 T22a–T22c，注入验红过：
- 去掉封顶 → T22b 红（`[65536, 262144]`）
- 到上限又改回 raise → T22 红（`EmptyContentError`）

## ⚠️ 并发上限（2026-10-23 重测，旧结论已作废）

**下面这段是旧参数下的结论，不要再用：**

> ~~6 并发是实测安全线，12 并发会被上游压死。12 并发时单条 80–95s、10/12 FAIL、
> `rpm exhausted` 累计 164 次。~~

旧结论测于 **24 张原图 + `max_tokens=65536`** 的配置下。2026-10-23 把参数改成
**8 张图 / 长边 1280 / 起始 8192** 之后重测：

| workers | 吞吐 | 429 次数 | 备注 |
|---|---|---|---|
| 6 | 2.5 片/分 | 0 | 太慢，1,800 片要 12 小时 |
| 16 | 4.0 片/分 | 0 | 还有余量 |
| **24** | **8.2 片/分** | 1 | 偶发 413 共 2 次 |

**为什么能推到 24**：每条请求的图片数与 token 预算都缩小了 3–4 倍，同一份 rpm 配额能装下更多请求。

**但有一个前提，比 workers 更关键：`DL_LLM_TIMEOUT` 必须设 240。**

用默认 900s 时，个别片会把上游挂死到超时，一个挂死片占住一个槽位整整 15 分钟。
实测 24 并发 + 900s：**101 秒只完成 9 片**，吞吐被几个挂死片拖到接近归零。
压到 240s 后 p50=133s / p90=286s，槽位周转正常。

```bash
export DL_LLM_TIMEOUT=240
python scripts/batch_vision.py --all --workers 24 --rounds 8
```

判断能否继续加：看 429 的**频次**。24 并发时 70 条里 429 只 1 次 → 还没触顶；
若 429 连续出现，先降 workers，不要先降 rounds。

## 失败片会不会永远跑不完？（2026-10-23 核查）

**结论：不会，且有兜底。**

日志里 FAIL 过的 164 片，**161 片后来重试成功**，只有 3 片尚未成功：

```
cc66598c371f  35图  429 rps exhausted
521a1d4f57a6  27图  429 rps exhausted
47a9f4dddcf9  14图  ReadTimeout
```

**全是瞬时错误，不是永久缺陷**。机制上：

1. `pick_pending()` 每轮**重新查库**取 `NOT EXISTS(slice_result)` 的片 →
   失败片自动进入下一轮，不需要额外处理
2. `--rounds 4` 意味着最多试 4 次
3. 万一 4 次全失败 → `finalize_p2.py` 报「未跑完」退出码 1 →
   `finish_phone2.py` 的闸门**阻止收尾**，不会被静默放过

所以最坏情况是「需要再跑一次 batch_vision」，而不是「数据残缺却当成完成」。

## ★ 修掉：「无画面描述」标注全错（2026-10-23 第 38 轮）

第 26/27 轮加的标注**判据是错的**，导致几乎所有片都被误标。

**实测 2026-07-21**：该日 123 片，全被标「无画面描述」，但实际只有 **9 片**真的没有。

### 根因

纯文本模式（`reader=text`）下，模型把画面细节**写进了 `overall_summary`**：

```
- 13:41:49-13:42:19：进入起点读书，停留在书架页面
- 浏览已收藏网络小说列表，包含《没钱修什么仙》《维校的三好》
```

而 `described_images` / `image_descriptions` / `image_tags` **三个字段全空**。
我原先的判据「structured.described_images 为空 → 判为无描述」因此**恒为真**。

### 修法

真值在**事件层** `event.payload.description`，不在 structured 里。

- `load_slices` / `slices_for_day` 读片时一并算出 `has_description`
- 两个 `_no_visual_basis()` 都改为读这个字段
- 字段缺失时返回 `False`（**宁可不标，也不错标**）

### 验证

```

日报「（无画面描述）」  123 → 9
```

注入「永远标注」→ T25a/c/d 同时红 → 还原复绿。冒烟 **143 / 0**。

**教训**：标注类功能上线后，必须抽查「标注数量」与「真实数量」是否同量级。
这次 123 vs 9 差了一个数量级，一眼就该看出来——我当初只验证了「标注出现」，没验证「标注对不对」。

## 修掉：build_daily 遇裸连接直接崩（2026-10-23）

**症状**：日报声明「视觉总结 0 片」，但库内该日 52/52 片都有总结。

**根因**：`daily.py` 内部大量用 `r["col"]` 取值，隐含要求连接带 `row_factory`。
用裸 `sqlite3.connect()` 调进来会崩在：

```
ValueError: dictionary update sequence element #0 has length 16; 2 is required
TypeError: tuple indices must be integers or slices, not str
```

`scripts/rebuild_daily.py` 自己设了 `row_factory` 所以没事，**但任何外部脚本一调就崩**，

**修法**：`build_daily` 入口统一兜底，不要求调用方记得设：

```python
if con.row_factory is None:

```

- **判断进度只能查库**，不要信 `ps`：MSYS2 下 `ps` 看不到 Windows 子进程，恒返回 0。
- 正确口径：`slice_result` JOIN `slice` WHERE `device='phone-2'` 的行数。
- 进程被静默杀掉时日志会**突然停在某一编号且无异常**——这时查库确认已落多少即可续跑。
- 用宿主托管的后台任务（`run_in_background`），不要用 shell 的 `&`，后者会随 shell 终止。
